# 项目需求文档（PRD）

## 1. 项目愿景

建设一个规模超过通用统一多模态工具包、面向医学模型与数据的开放平台，同时保证“规模”不以牺牲可运行性、医学语义、数据治理和证据真实性为代价。

## 2. 目标用户

- 医学多模态模型研究者：统一运行和比较不同架构。
- 数据与评测研究者：定义任务专属、可审计的医学协议。
- 平台开发者：通过稳定接口添加模型、数据、指标、后训练和后端。
- 工程团队：在本地、Slurm 和多 GPU 环境中复现实验。

## 3. 核心需求

### FR-1 统一组件接口

系统必须提供模型、数据集、基准、指标和后训练抽象；组件应通过惰性注册发现，重量级依赖不得在目录查询阶段导入。

### FR-2 三类执行任务

系统必须支持理解、生成、编辑，并在模型加载前校验能力、模态、图像数量和批大小。

### FR-3 医学语义与指标

系统必须支持超越自然图像分类的医学任务，包括 VQA、报告事实、定位、测量、校准、选择性预测和分组分析。缺失所需标注时必须显式 unavailable。

### FR-4 可审计评测

系统必须支持 `audit → generate → score → report`，记录模型/数据/协议指纹，拒绝不匹配缓存，并保留逐样本结果。

### FR-5 资源规模

模型和数据目录均应超过 20 项，并记录官方来源、论文/代码、许可、访问级别、任务、模态、医学领域、revision 策略和验证状态。

### FR-6 后训练

系统必须支持通用医学对齐目标及多阶段研究路线。计划、contract smoke、官方/参考运行时和论文复现必须分开表述。

### FR-7 高性能推理

系统必须支持 vLLM/SGLang 连续批处理，公开 TP/PP/DP 配置和性能报告；Emu3.5 的 CFG 必须使用其兼容的 cond/uncond 调度路径，不能静默降级。

### FR-8 CLI 与 Python API

CLI 与 Python API 必须共享编排实现。所有主要流程由 YAML 配置驱动，并允许有限的命令行覆盖。

### FR-9 分布式与调度器

运行时必须识别 Slurm/torchrun，确定 rank/world size，支持确定性分片和严格预测合并。多节点执行必须在有证据前保持未完成状态。

### FR-10 报告与版本证据

每个里程碑必须同时提供自动测试、机器可读证据、环境和版本、成功范围、失败记录与限制。

## 4. 非功能需求

| 维度 | 要求 |
|---|---|
| 可复现性 | 固定源码、模型、数据和协议 revision；运行清单可追溯 |
| 安全与隐私 | 医学数据必须声明许可、去标识化、来源和访问条件 |
| 兼容性 | 公共 schema 的破坏性变更需要新版本与迁移路径 |
| 可扩展性 | 新组件不应要求修改无关执行层；冲突依赖允许隔离 bridge |
| 可观测性 | 记录延迟、吞吐、Token、GPU、主机、Slurm、失败原因 |
| 诚实性 | catalog/interface/smoke/runtime/quality 不得互相替代 |
| 临床边界 | 默认 research-only，不产生医疗器械或诊疗用途声明 |

## 5. 完成定义

一个新垂直切片只有同时满足以下条件才算完成：

1. 模型和数据分别拥有稳定注册名与明确来源；
2. 使用不可变 revision 和独立环境；
3. 数据通过许可、来源、去标识化与结构审计；
4. 真实模型在目标硬件生成非空输出；
5. 专属协议产生逐样本及聚合指标；
6. 测试、配置、脚本和机器可读证据提交到 Git；
7. 文档说明样本规模、验证等级、失败和限制。

## 6. 非目标

- 不自动授予受限医学数据或模型权重的使用权。
- 不以少量 smoke 样本发布医学效果结论。
- 不把第三方源码无差别复制进主仓库。
- 不承诺任意模型都能在同一个 Python 环境运行。
- 不把平台输出直接用于诊断或治疗。
