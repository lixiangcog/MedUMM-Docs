# 四层架构

MedUMM 与统一多模态工具包的总体分层一致：依赖从上层向下选择，数据和结果从底层向上返回。

```{mermaid}
flowchart BT
  subgraph L4[基础设施层]
    I[抽象接口]
    C[运行时 / 分布式 / 指标 / 审计 / I/O]
    B[PyTorch / Transformers / Diffusers / 原生运行时]
  end
  subgraph L3[核心功能层]
    M[模型统一接口]
    D[医学基准数据集]
    P[后训练方法]
  end
  subgraph L2[任务与执行层]
    U[多模态理解]
    G[多模态生成]
    E[多模态编辑]
    X[跨任务评测]
  end
  subgraph L1[应用与 API 层]
    Y[YAML 统一配置]
    A[CLI 与 Python API]
    R[报告与排行榜]
  end
  L4 --> L3 --> L2 --> L1
  L1 -.选择依赖.-> L2
  L2 -.选择组件.-> L3
```

## 应用与 API 层

用户通过 YAML、`medumm` CLI 或 Python API 发起工作。每次运行都会创建 `RuntimeContext`，并将非秘密环境、组件、配置和结果写入运行清单。

## 任务与执行层

通用执行任务只有三种：理解、生成、编辑。医学语义是另一个正交维度。例如“生成放射报告”在输出模态上仍是文本理解，而不是图像 generation。

## 核心功能层

四个惰性注册表管理模型、数据集、基准和训练器。模型在加载权重前声明支持的任务、模态、批处理、后端和并行方式，因此不兼容请求会尽早失败。

## 基础设施层

稳定抽象类定义生命周期；运行时解析设备、Slurm/torchrun rank、输出目录和实验身份；数据审计、版本指纹、原子文件写入和指标套件属于公共基础设施。

## 为什么这样分层

当一个新模型加入时，不需要重写评测状态机；当一个新医学指标加入时，不需要改模型加载；当后端从原生推理切到 vLLM/SGLang 时，上层请求与结果仍然稳定。
